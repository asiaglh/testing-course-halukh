# ЛР 8 — нестабільність E2E-тестів

**Галух Анна Олександрівна, 63М.** Один сценарій додавання студента виконано по 20 разів у двох варіантах. Наївний читає `students.message.text_content()` одразу після кліку; другий застосовує `expect(students.message).to_have_text(...)`.

| Тест | `PORTAL_MAX_DELAY` | Впало з 20 | Причина | Виправлення |
| --- | ---: | ---: | --- | --- |
| `test_naive_text_right_after_click` | 0 | **20** | Клік завершується до асинхронного `fetch` і появи повідомлення. Одне миттєве читання бачить порожній `status`. | Замінити на перевірку з автоматичним очікуванням. |
| `test_web_first_assertion` | 0 | **0** | `expect` дочікується тексту після відповіді API. | Залишити `expect`. |
| `test_naive_text_right_after_click` | 0.3 с | **20** | Випадкова затримка відповіді збільшує вікно між кліком і оновленням DOM. | Замінити на `expect`. |
| `test_web_first_assertion` | 0.3 с | **0** | Повторні перевірки охоплюють затримку. | Залишити `expect`. |

```sh
cd app
FLAKY_DEMO=1 uv run pytest -q tests/lab08/test_flaky.py
FLAKY_DEMO=1 PORTAL_MAX_DELAY=0.3 uv run pytest -q tests/lab08/test_flaky.py
```

Підсумки запусків: **20 failed, 20 passed** за 11,12 с без затримки та **20 failed, 20 passed** за 28,33 с із затримкою. Наївний тест пропускається без `FLAKY_DEMO=1`, тому демонстрація не робить CI червоним. Цей результат показує детерміновану гонку в обраному середовищі; слово «нестабільність» описує ризик залежності результату від швидкості, навіть якщо тут усі 20 наївних повторів впали.

`test_ui.py` з `PORTAL_MAX_DELAY=0.3` запущено **тричі**: кожного разу **16 passed, 9 xfailed** (34,37 с; 33,36 с; 32,58 с). Без затримки результат той самий. Очікування готовності списку прив'язане до позитивної ознаки `Усього: N`; підрахунок рядків для порівняння береться лише після цього. Для скасування видалення тест стежить за запитами DELETE — негайне `to_be_visible()` саме по собі не довело б відсутність асинхронної дії.

`xfail` за відомими дефектами може чекати стандартні 5 с на кожній помилковій умові. Для підтверджених відмов, після позитивної ознаки завершення дії, очікування скорочено до 1,5 с; це прискорює набір і лишає запас понад максимальні 0,3 с затримки API. Наївні 20 повторів у CI пропущено.
