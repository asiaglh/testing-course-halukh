# ЛР 7 — контракт деканату й API

**Галух Анна Олександрівна, 63М.** Споживач: `dean-office`, провайдер: `student-portal`. Контракт Pact V4: [`dean-office-student-portal.json`](../../app/tests/lab07/contract/pacts/dean-office-student-portal.json). Обидві взаємодії записані в одному файлі. Тести споживача викликають справжню `fetch_student_card` проти Pact mock server; тест провайдера відтворює цей файл проти справжнього локального API.

| Взаємодія / стан | Тест споживача | Перевірка провайдера | Причина відмови | Хто має змінити | Issue |
| --- | --- | --- | --- | --- | --- |
| id 1, студент має оцінки; `average=92.5`, `funding=державне замовлення` | Пройдено: `StudentCard("Коваль Олена", ..., "92.5", True)` | Очікувана відмова: немає `funding` | Провайдер повертає дані за Р-23, але контракт Р-24 вимагає додаткового поля | Команди API та деканату мають узгодити Р-23/Р-24; після зміни специфікації команда API додає поле або окремий контрактний endpoint | [#37](https://github.com/asiaglh/testing-course-halukh/issues/37) |

`fetch_student_card` також має прокидати HTTP-помилки як `httpx.HTTPStatusError`; `contract/test_dean_error.py` перевіряє це для 404. Стани Pact прив'язані до наявних записів у копії навчальних даних, тому обробники станів не змінюють базу.

Р-23 вимагає **рівно** шість полів студента (`id`, `first_name`, `last_name`, `email`, `group`, `average`), тоді як Р-24 вимагає від тієї самої відповіді ще й `funding`. Отже, просте додавання поля зламає сувору перевірку Р-23. Потрібна зміна домовленості між командами або окреме подання; лише після цього можна виправити провайдера й оновити незалежну схему тесту. `xfail(strict=True)` зберігає зеленим CI з відомими дефектами та перетвориться на XPASS після їх усунення, що вимагатиме перегляду очікувань.

```sh
cd app
uv run pytest -q tests/lab07/contract
```

Результат локально: два Pact тести споживача (один пройшов, один очікувано впав), перевірка провайдера очікувано впала, тест HTTP-помилки пройшов. Зафіксований контракт містить **дві** взаємодії; тестова фікстура очищає файл перед модулем і додає кожну взаємодію через `write_file`, тому результат відтворюваний. Це контрактна перевірка сумісності; вона не замінює повний інтеграційний тест двох запущених сервісів, який також перевіряв би мережеву конфігурацію та розгортання.
