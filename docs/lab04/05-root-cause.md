# Аналіз першопричини: частковий CSV-імпорт (#5)

Галух Анна Олександрівна, 63М. Дефект [#5](https://github.com/asiaglh/testing-course-halukh/issues/5), серйозність **критична**. Відтворення: у групі 5 студентів файл `test-data/invalid-last-row.csv` містить валідний рядок 2 та невалідне фінансування у рядку 3. Консоль повідомляє `Помилка введення: рядок 3: фінансування має бути «бюджет» або «контракт»`, але після пункту 0 збережено 6 студентів. [Протокол](evidence/session1/invalid-last-row.csv-repro.txt), [CSV](test-data/invalid-last-row.csv). Файл із відсутнім email у рядку 3 та файл із точним дублем у рядку 3 дають таку саму часткову зміну.

## П’ять «чому»

1. **Чому порушена Р-19?** Після помилки у пізньому рядку в групі лишається студент із попереднього валідного рядка.
2. **Чому він лишається?** `import_students` у `app/src/student_portal/importer.py` викликає `group.add(student)` прямо всередині циклу читання. До помилки група вже змінена.
3. **Чому помилка не відкочує зміну?** Імпортер не збирає рядки у тимчасовий список і не має механізму відкату. `dean.run` ловить `PortalError` і продовжує роботу з уже зміненою групою; пункт 0 записує її в JSON.
4. **Чому ця поведінка пройшла перевірки?** У `app/tests/test_importer.py` є позитивний зразок, порожнє фінансування й неправильний заголовок. Остання помилка стається **до** додавання першого студента. Тесту помилки у другому або останньому рядку з порівнянням групи до/після немає.
5. **Чому такого тесту не було?** Імовірна прогалина в перетворенні умови «якщо хоча б один рядок має помилку, не додається жоден студент» на критерій приймання та набір негативних сценаріїв. Це **гіпотеза про процес**, а не встановлений факт про дії розробника; її слід перевірити з автором застосунку.

## Дія для запобігання

- Реалізувати двофазний імпорт: спочатку розібрати й перевірити всі рядки та регістронезалежну унікальність в окремій колекції, потім однією логічною дією додати їх до групи. Для помилки на будь-якому етапі стан `Group` має дорівнювати початковому.
- Додати до обов’язкової перевірки PR сценарії: невалідний рядок 1, 2, останній; повтор email у файлі й групі; перевірка повного знімка студентів, а не лише типу винятку. Перевіряти через API та консоль із повторним читанням JSON після пункту 0.
- На огляді вимог позначати атомарність окремим пунктом матриці Р-19 → тест → очікувана незмінність; не вважати тест неправильного заголовка достатнім для цієї умови.

Застосунок у цій лабораторній не змінено. Пропозиції вище — дії для розробника і процесу приймання, а не виконане виправлення.
